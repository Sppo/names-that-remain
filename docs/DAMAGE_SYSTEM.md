## 1. Призначення та статус правил

Документ фіксує універсальний розрахунок шкоди для героїв і ворогів. Він спирається на обговорення «Чат Концепція командної гри» та поточний запит на оформлення моделі. Короткий статус — `docs/GDD.md`, §7.5. Код і `docs/COMBAT_SPEC.md` цієї формули не виконують.

Чинний бій кидає влучання і блок цілими числами від 1 до 100: влучання і блок, якщо кидок не більший за шанс. У цьому файлі нове уточнення інше: випадкове число з проміжку `[0, 1)`, успіх якщо воно строго менше за шанс. Рівність порогу в уточненні — промах. 29 жовтня 2026 це уточнення не прийнято: і для нової моделі кидок лишається цілим 1–100, успіх при `roll <= chance` (`docs/STARTING_ABILITIES_DETAILS.md`, §3.5).

Позначення статусу:

- **[Наявне за обговоренням]** — правило описувалося як уже реалізоване. Перед майбутньою реалізацією потрібно звірити його з кодом і бойовою специфікацією.
- **[Поточна модель]** — нове правило бойової математики, яке цей документ фіксує за поточним запитом. Це не твердження, що воно вже є у грі.
- **[Нове уточнення]** — запропонована тут точна домовленість для однозначного алгоритму й тестів; не видається за раніше погоджене правило.
- **[Відкрите питання]** — рішення ще немає; не реалізовувати власний варіант без узгодження.

| Правило | Статус |
| --- | --- |
| Влучання: точність мінус ухилення, обмеження 5–95% | Наявне за обговоренням |
| Окремий кидок блоку після влучання; блок ділить шкоду навпіл із відкиданням дробу | Наявне за обговоренням |
| «Прикрити»: одноразовий запас 10; промах не витрачає, перше влучання витрачає весь запас | Наявне за обговоренням |
| Прикриття не переносить атаку або втрату HP на захисника | Наявне за обговоренням |

| Точний порядок отримання випадкових значень, межі кидків, обробка нульового влучання, вхідні обмеження та завершення HP | Нові уточнення цього документа. Кидки і їх порядок закриті 29 жовтня 2026 у `docs/STARTING_ABILITIES_DETAILS.md`, §3.5, не за моделлю `[0, 1)` |

У розмові раніше траплялися інші кандидати формул і заборона додавати броню. Для цієї специфікації їх замінює поточна модель нижче. Це не дозвіл автоматично переписати стару реалізацію.

## 2. Основна формула

**[Поточна модель]**

```text
Damage = round_half_up(
    BaseDamage × AbilityMultiplier × StatScaling
    × AttackerModifiers × TargetModifiers
)

P = STR × wSTR + DEX × wDEX + KNO × wKNO
StatScaling = 1 + (P − 3) / (P + 7)
```

`Damage` — ціла шкода **до броні, блоку та прикриття**, а не остаточна втрата HP.

| Величина | Значення |
| --- | --- |
| `BaseDamage` | Один випадковий цілий результат із базового діапазону зброї або здібності |
| `AbilityMultiplier` | Коефіцієнт конкретної здібності |
| `STR`, `DEX`, `KNO` | Значення характеристик атакувальника, надані розрахунку |
| `wSTR`, `wDEX`, `wKNO` | Невід'ємні ваги здібності; сума дорівнює 1 |
| `P` | Вагова комбінація характеристик; може бути дробовою |
| `StatScaling` | Множник характеристик |
| `AttackerModifiers` | Уже визначений сукупний множник завданої шкоди |
| `TargetModifiers` | Уже визначений сукупний множник отримуваної шкоди |

Без модифікаторів `AttackerModifiers = TargetModifiers = 1`. Броня, блок і прикриття не входять до `TargetModifiers`: інакше захист буде враховано двічі.

Базовий діапазон береться з одного джерела, визначеного здібністю: зброї **або** самої здібності. Формула не передбачає автоматичного додавання шкоди зброї до шкоди здібності.

Ваги задаються для здібності, а не для класу загалом. Для ножа Мисливця стартовий тестовий баланс — 0,6 Вправності і 0,4 Сили, запис `docs/HUNTER_ABILITIES.md`. «Прицільний постріл» масштабується лише від Вправності. Приклад із коефіцієнтом 1,4 нижче лишається ілюстрацією формули, не параметром ножа. Масштабування лікування — `docs/ACCURACY_DODGE_HEALING_SYSTEM.md`; воно не проходить через броню, блок і прикриття.

### 2.1. Властивості масштабування

| `P` | Точний або приблизний `StatScaling` |
| --- | --- |
| 0 | `4/7 ≈ 0.571429` |
| 1 | `0.75` |
| 3 | `1` |
| 4.2 | `31/28 ≈ 1.107143` |
| 5 | `7/6 ≈ 1.166667` |
| 10 | `24/17 ≈ 1.411765` |
| 20 | `44/27 ≈ 1.629630` |

За невід'ємного `P` множник додатний, зростає зі спадною віддачею та наближається до 2 знизу. Значення в таблиці для показу; у розрахунках використовувати повну точність. Не округлювати `P` до цілого й не усереднювати окремо обчислені множники STR, DEX та KNO.

## 3. Вхідні дані та округлення

**[Нове уточнення]** Для описаного алгоритму допустимі:

- Цілі `BaseMin`, `BaseMax`: `0 ≤ BaseMin ≤ BaseMax`.
- Скінченні невід'ємні STR, DEX, KNO, ефективна броня `ARM` та всі множники.
- Скінченні невід'ємні ваги із сумою 1; не нормалізувати помилкові ваги мовчки.
- Цілі невід'ємні `CurrentHP` і запас прикриття; `CurrentHP ≤ MaxHP`.
- Шанс блоку в межах 0–100%; він не є значенням ARM.

Ці обмеження задають область визначення обчислення, а не стартову шкалу чи правила прокачування. Мінімальні характеристики, негативні ефективні характеристики або негативна броня потребують окремого рішення. Некоректні дані мають бути явно відхилені до кидків і зміни стану; не перетворювати їх довільно на нулі чи одиниці. Спосіб повідомлення помилки залежить від проєкту.

**[Поточна модель]** Для невід'ємного `x`:

```text
round_half_up(x) = floor(x + 0.5)
```

Приклади: `2.49 → 2`, `2.5 → 3`, `3.5 → 4`. Не використовувати банківське округлення, де половини прямують до парного числа.

Є лише два етапи half-up:

1. Після повного добутку основної формули.
2. Після застосування фізичної броні.

`P`, `StatScaling`, окремі множники, проміжні добутки й частку броні не округлювати. Блок використовує окреме правило `floor(D / 2)`. Прикриття та віднімання HP працюють із цілими числами.

**[Нове уточнення]** Реалізація повинна відтворювати математичне half-up і на точних половинах. Не додавати довільний epsilon до всіх чисел: він може змінити результат значень нижче половини. Конкретний числовий тип обирається під час реалізації; граничні випадки нижче обов'язкові для перевірки.

## 4. Випадковість і порядок кидків

**[Поточна модель]** Базова шкода рівномірно обирається серед **цілих** чисел включного діапазону:

```text
BaseDamage ∈ {BaseMin, BaseMin + 1, …, BaseMax}
Pr(BaseDamage = b) = 1 / (BaseMax − BaseMin + 1)
```

Не обирати довільне дробове число з подальшим округленням: це дає інший розподіл. Не обирати рівномірно результат із уже масштабованого діапазону: різні базові значення можуть округлюватися в однакову шкоду.

**[Не прийнято 29 жовтня 2026]** Модель `[0, 1)` і пропуск кидка блоку при 0% або 100% нижче не прийняті. Чинне правило — `docs/STARTING_ABILITIES_DETAILS.md`, §3.5: ціле 1–100, успіх якщо кидок не більший за шанс; порядок — влучання, база шкоди (лише якщо в діапазоні більше одного значення), блок; кидок блоку на кожному фізичному влучанні, навіть при 0%. Так зерна контрольного бою не зсуваються. Текст нижче лишається як історія пропозиції.

**[Нове уточнення, не прийняте]** Для однієї звичайної атаки по одній допустимій цілі пропонувався такий порядок запитів до джерела випадковості:

1. **Влучання.** Отримати `uHit ∈ [0, 1)`. Влучання, якщо `uHit < HitChance / 100`, де чинний `HitChance = clamp(Accuracy − Dodge, 5, 95)`. Рівність порогу означає промах.
2. **Базова шкода.** Лише після влучання отримати рівномірне ціле `BaseDamage`. Для `BaseMin = BaseMax` взяти константу без випадкового кидка.
3. Обчислити основну шкоду й застосувати броню.
4. **Блок.** Якщо `0 < BlockChance < 100`, отримати окреме `uBlock ∈ [0, 1)`; блок спрацьовує, якщо `uBlock < BlockChance / 100`. За 0% блок не спрацьовує, за 100% спрацьовує без кидка. Це не нове право персонажів мати 100% блоку, а визначення меж алгоритму.
5. Прикриття й HP не потребують кидків.

Після промаху не кидати базову шкоду або блок і не витрачати прикриття. За успішного влучання крок блоку виконується навіть при `Damage = 0`; прикриття теж обробляється. Це **нове уточнення нульового влучання**. Кидок блоку на кожному фізичному влучанні і витрата прикриття влучанням, яке після блоку знімає 0, затверджені (`docs/STARTING_ABILITIES_DETAILS.md`, §3.3, §3.5). Відкрите лише влучання, у якого шкода до броні вже 0 через модифікатори (розділ 8, п. 6).

Кидки мають бути окремими, без повторного використання значення влучання для блоку чи шкоди. Відтворюваність потребує однакового початкового стану генератора та однакового порядку його викликів. Ця специфікація фіксує порядок логічних запитів, а не кількість внутрішніх операцій генератора. Алгоритм і seed генератора тут не обираються. Перед міграцією перевірити вплив нового порядку на наявні повтори боїв.

Нові бонуси DEX до точності або ухилення тут не вводяться. Формули `+2 × (DEX − 3)` та `+(DEX − 3)` затверджені 29 жовтня 2026 у `docs/ACCURACY_DODGE_HEALING_SYSTEM.md` і `docs/STARTING_ABILITIES_DETAILS.md`, §3.5.

## 5. Порядок захисту й завершення шкоди

```text
Перевірка допустимості атаки та даних
→ кидок влучання
→ базова шкода
→ повний добуток і round_half_up
→ фізична броня і round_half_up, за потреби мінімум 1
→ кидок блоку та floor(шкода / 2)
→ одноразове «Прикрити»
→ віднімання поточного HP
```

### 5.1. Фізична броня

**[Поточна модель]** `ARM` — ефективна броня саме обраної цілі.

```text
Reduction = ARM / (ARM + 20)
RemainingFraction = 20 / (ARM + 20)

якщо Damage = 0:
    AfterArmor = 0
інакше:
    AfterArmor = max(1, round_half_up(Damage × RemainingFraction))
```

Мінімум 1 перевіряється за **цілим `Damage` після першого округлення**. Якщо додатний сирий добуток округлився до 0, броня не повертає йому 1. Якщо будь-який множник дорівнює 0, шкода також залишається 0.

За `ARM = 0` броня не змінює шкоду. За скінченного невід'ємного ARM формула не дає 100% зменшення. Ліміт захисту 75% не затверджено й у цій моделі не застосовується.

Цей етап нормативно описаний для фізичної шкоди. Особлива шкода, зокрема обряд Культиста, броню обходить — `docs/DAMAGE_TYPES_SYSTEM.md`.

### 5.2. Блок

**[Наявне за обговоренням]**

```text
AfterBlock = floor(AfterArmor / 2)  // якщо блок спрацював
AfterBlock = AfterArmor            // якщо блок не спрацював
```

Блок — окремий шанс, а не постійне відсоткове зменшення. Наприклад, блок 25% означає шанс спрацювання 25%, а не постійне зменшення шкоди на 25%. Після броні `1` при блоці перетворюється на `0`. Мінімум 1 повторно не застосовується.

### 5.3. «Прикрити»

**[Наявне за обговоренням]** Чинний одноразовий запас — `CoverAmount = 10`.

```text
якщо є активне прикриття й атака влучила:
    Absorbed = min(AfterBlock, CoverAmount)
    FinalDamage = AfterBlock − Absorbed
    зняти прикриття повністю
інакше:
    Absorbed = 0
    FinalDamage = AfterBlock
```

Якщо удар після блоку становить 3, прикриття поглинає 3 і зникає; залишок 7 не переноситься на наступний удар. Якщо удар становить 14, поглинається 10, ціль отримує 4. Промах зберігає прикриття. Атака залишається спрямованою на обрану ціль; захисник не отримує перенаправлену шкоду.

**[Нове уточнення]** Влучання, яке завдало 0 після множників або блоку, теж знімає прикриття: критерієм є факт влучання, а не додатна втрата HP. Тривалість, повторне накладання та взаємодія кількох прикриттів цим документом не змінюються.

### 5.4. Поточне HP

**[Нове уточнення]**

```text
HPBefore = CurrentHP
HPAfter = max(0, HPBefore − FinalDamage)
ActualHPLoss = HPBefore − HPAfter
Overkill = FinalDamage − ActualHPLoss
```

`FinalDamage` і `ActualHPLoss` можуть відрізнятися: удар на 7 по цілі з 3 HP забирає 3 HP, надлишок становить 4. Шкода не лікує й не змінює MaxHP. Мінімальну шкоду після блоку чи прикриття не відновлювати.

Якщо HP стало 0, передати результат чинним правилам вибуття/смерті й завершення бою. Цей документ не вводить нових правил смерті, посмертних ефектів або нагород. Допустимість атаки по вже вибулій цілі визначає чинна бойова система до кидків.

## 6. Розібрані приклади

Усі числа здібностей та зброї нижче — тестові, не остаточні характеристики персонажів.

### A. Базовий меч і вплив характеристики

`BaseMin = 4`, `BaseMax = 6`, `STR = 5`, ваги `(1, 0, 0)`, коефіцієнт здібності й обидва модифікатори — 1.

```text
P = 5
StatScaling = 1 + 2/12 = 7/6
B = 4 → round_half_up(14/3) = 5
B = 5 → round_half_up(35/6) = 6
B = 6 → round_half_up(7)    = 7
```

Кожен із результатів 5, 6, 7 має ймовірність 1/3 за умови влучання. Тут показано шкоду до захисту. За коефіцієнта здібності `1.4` результати становлять відповідно 7, 8, 10; значення 9 не виникає. Отже, не можна замінити цей розрахунок рівномірним кидком від 7 до 10.

### B. Гібридна здібність і два готові модифікатори

`STR = 3`, `DEX = 5`, ваги `(0.4, 0.6, 0)`, випало `B = 5`, `AbilityMultiplier = 1.4`, `AttackerModifiers = 1.25`, `TargetModifiers = 1.2`, `ARM = 5`, без блоку та прикриття.

```text
P = 3 × 0.4 + 5 × 0.6 = 4.2
StatScaling = 31/28
RawDamage = 5 × 1.4 × (31/28) × 1.25 × 1.2 = 11.625
Damage = 12
AfterArmor = round_half_up(12 × 20/25) = 10
FinalDamage = 10
HP: 20 → 10
```

Множники 1.25 та 1.2 задано готовими входами. Приклад не затверджує правила складання кількох бафів усередині кожної категорії.

### C. Броня, блок і прикриття разом

`Damage = 14`, `ARM = 5`, блок спрацював, активне прикриття 10, `HPBefore = 20`.

```text
AfterArmor = round_half_up(14 × 20/25) = round_half_up(11.2) = 11
AfterBlock = floor(11/2) = 5
Absorbed = min(5, 10) = 5
FinalDamage = 0
HPAfter = 20
Прикриття знято повністю.
```

### D. Мінімальна шкода та нуль

`Damage = 1`, `ARM = 100`:

```text
AfterArmor = max(1, round_half_up(1 × 20/120)) = 1
Без блоку й прикриття: FinalDamage = 1
З успішним блоком: FinalDamage = floor(1/2) = 0
```

Якщо натомість `Damage = 0`, результат після броні — 0 незалежно від ARM. Броня не створює шкоду.

## 8. Відкриті питання — не заповнювати припущеннями

1. **Складання відсоткових модифікаторів.** Принципи записані в `docs/STATUS_EFFECTS_SYSTEM.md`: внески однієї категорії додаються, сума обмежується −60%…+100%, множники різних категорій перемножуються. Ця формула шкоди й далі приймає вже зібрані `AttackerModifiers` і `TargetModifiers`. Змішання абсолютного бонуса з відсотком затверджено: `(BaseStat + плоскі) × (1 + відсотки)`, без округлення.
2. **Ефективні характеристики та броня.** Чи дозволені від'ємні результати; які мінімальні й максимальні значення? Поки не вводити «Розкол броні», пробиття чи нові обмеження.
3. **Типи шкоди.** Закрито в `docs/DAMAGE_TYPES_SYSTEM.md`: фізична і особлива; обряд Культиста особливий і броню обходить. Не додавати автоматично магічну, істинну, отруйну шкоду чи опори.
4. **Баланс здібностей.** Діапазони, коефіцієнти й ваги дванадцяти здібностей героїв, удару щитом, кігтів і обряду — `docs/STARTING_ABILITIES_DETAILS.md`. Там же стріла і базовий удар Культиста та «Добивання». Числа прикладів цього файлу не є балансом.
5. **Критичні удари, періодична шкода, кілька цілей і серії ударів.** Чи потрібні вони та як проходять кидки, захист і споживання прикриття? Алгоритм цього документа описує один звичайний удар по одній цілі.
6. **Нульове влучання й порядок RNG.** Порядок RNG закрито (розділ 4). Влучання, яке після блоку знімає 0, прикриття витрачає. Відкрито лише влучання, у якого шкода до броні вже 0 через модифікатори.
7. **Точність, ухилення та лікування.** Формули записані в `docs/ACCURACY_DODGE_HEALING_SYSTEM.md`. Бази і стартова Вправність шістьох — `docs/STARTING_ABILITIES_DETAILS.md`. Випадковий діапазон шкоди на звичайне лікування не переносити.
8. **Зміна HP поза отриманням шкоди.** Зміни MaxHP, лікування, вибуття й пов'язані ефекти залишаються за окремими специфікаціями.
