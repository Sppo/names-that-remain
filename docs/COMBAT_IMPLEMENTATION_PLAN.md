# План реалізації нової бойової моделі

**Статус:** погоджено власником 30 жовтня 2026 як основа реалізації. Кожна фаза починається лише після окремого дозволу. Дозвіл на одну фазу не дає дозволу на наступну.

**Джерела правил:** `docs/STARTING_ABILITIES_DETAILS.md` — чинна консолідована специфікація; короткий реєстр — `docs/GDD.md`, §7.5; контракт — `docs/ARCHITECTURE.md`, розділ «Розширення для цільової моделі». Контрольний бій описує `docs/COMBAT_SPEC.md`. Якщо старіший документ суперечить `STARTING_ABILITIES_DETAILS.md`, чинний останній.

**Ролі:** `/core` — контракт і `scripts/core/`; `/combat` — правила, ШІ, сценарії і тести в `scripts/combat/`, `tests/combat/`; `/ui` — `scenes/` і `assets/`; `/checker` — незалежна перевірка, код не змінює. Оркестратор координує і нічого не комітить без дозволу.

## Незмінні межі

- **Контрольний бій 3 на 3 заморожений.** Склад, позиції, стартові числа, id здібностей, шкода, швидкості, черга, порядок і кількість звернень до генератора, послідовність подій і кінцевий стан генератора не змінюються. `create_opening_battle()` лишається як є. Старі очікування тестів не редагуються під нові картки.
- **Новий бій — окремий сценарій** поруч із контрольним, зі своїми картками, формулами й очікуваннями.
- **Навмисний тактичний програш — не баг.** Після смерті позиція лишається порожньою. Ворогів не підтягують, дальність атак не розширюють, переможця не гарантують. Якщо живий герой не дістає живого ворога через попередні рішення гравця, це задуманий наслідок.
- **Ліміт раундів у тесті** лише зупиняє прогін і фіксує стан для аналізу. Незавершений бій на межі сам не означає поразку, перемогу чи помилку. Тактичну недосяжність треба відрізняти від технічного зависання: невалідної команди ШІ, зупиненої черги, нескінченного обміну без прогресу.
- **Без рішення власника не додавати** відступ, здачу, авто-рух, примусову перемогу, нові стани, нові механіки.
- Нові кидки — ціле 1–100, успіх при `roll <= chance`. Порядок: влучання, потім база шкоди лише для діапазону, потім блок на кожному фізичному влучанні навіть при 0%. Гарантований обряд не кидає нічого.
- Дробові обчислення рахувати точно. На межі половини є реальні випадки: поштовх із базою 3 при Силі 5 дає рівно 3,5 → 4; шкода 3 крізь броню 4 дає рівно 2,5 → 3.
- Без комітів і push без окремого дозволу.

## Загальна перевірка кожної фази

```
godot --headless --path /Users/sppo/custom_games/NamesThatRemainV1 -s res://addons/gut/gut_cmdln.gd -gdir=res://tests/combat -gexit
```

- Повний `tests/combat` зелений, число тестів і перевірок записане з реального запуску.
- Еталон контрольного бою з фази 0 проходить без змін очікувань.
- Checker звіряє результат фази з цим планом і специфікацією за файлами і запуском.
- Ніхто не заявляє успіх без фактичного запуску.

**Відповідальні:** `/core` — контракт контролера і програвача подій у `docs/ARCHITECTURE.md`; `/ui` — сцени в `scenes/` і `assets/`; `/checker` перевіряє.

**Завдання:**
1. Core описує невізуальний контролер бою: створення бою, команда гравця, ходи ворогів, явний стан помилки при відхиленій команді.
2. Перенести з екрана в контролер генератор, `CombatRules`, `EnemyAi` і цикл ворожих ходів.

6. Один `Theme.tres` замість кольорів і стилів у коді.
7. Шляхи портретів — у візуальних даних бійця, не в константі екрана.
8. Перенесення каталогу і складу бою в `.tres` — лише окремим рішенням Core; у цій фазі не обов'язкове.

**Залежності:** фаза 1 (вона ще змінює `combat_screen.gd`). Механіки фаз 2–8 тут не показуються.

**Тести:** контролер без графіки — повний бій контрольного сценарію з фіксованим зерном дає той самий підсумок, що еталон; відхилена ворожа команда дає стан помилки, а не зависання; сцена бою створюється; один хід гравця і ворога програються до кінця.

**Готово, коли:** еталон фази 0 без змін; контрольний бій грається і читається як раніше; у сценах немає ігрової логіки, у контролері — візуальних вузлів; власник переглянув вигляд.
